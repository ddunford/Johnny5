# Lessons

### "Idle in chat" ≠ "not running"; and killing `./ctl.sh test`'s bash does NOT stop its container
Two-part lesson from a Phase 6a collision. (1) A teammate running `./ctl.sh test` (esp. a 3× loop) as a **detached background job** shows IDLE in team chat — its chat-turn ended, but its pytest container is still hammering `johnny5_test`. The lead misread a QA idle notification as "DB free," launched a verification `./ctl.sh test`, and collided with QA's in-flight run 2. **Before taking the test-DB window, confirm `docker ps | grep -E 'api-run|test'` shows no live runner** — never infer "free" from chat-idle (idle teammate + live test container = still running). (2) `./ctl.sh test` spawns a detached `docker compose run … johnny5-api-run-*` container; **`TaskStop`/killing the launching bash does NOT stop that container** — it kept running pytest for 12 min and *did* corrupt the concurrent run 2 (17 rotating failures, all in pre-existing `tests/sleep/`, zero in the phase's new files — the textbook contention signature, since the same tests passed in runs 1 & 3 on identical code). To actually stop a stray run you must `docker kill johnny5-api-run-<id>`, then verify `docker ps` is clear. Diagnosis tell: a real regression fails deterministically in every pass; a mid-run-only rotating failure set = a second runner interleaving TRUNCATEs.

### Teammates never run destructive git on the shared working tree (single-committer model)
In a `/team-execute` run the lead is the SOLE committer; teammates implement + report, the lead commits. A teammate must therefore never run `git checkout`/`restore`/`reset`/`clean` (or any tree-mutating git) on the shared working tree — not even to "revert" their own work. The lead may be holding uncommitted edits in those files, and a `git checkout HEAD -- <file>` would silently wipe them. In Phase 6a a teammate ran `git checkout HEAD -- <5 files>` to undo an addendum after a superseded ruling; it happened to be a no-op (the files were already committed) but it was a live risk. If something needs reverting, the teammate asks the lead to do it. (Spawn-prompt teammates with this explicitly.)

### Run `ruff format --check` before committing teammate code
As the single-committer lead, a teammate reporting "ruff/mypy clean" usually means `ruff check` (lint) + `mypy`, NOT `ruff format`. They're separate gates and CI runs both. Phase 1 committed 5 `brain/memory/*.py` files that passed lint but failed `ruff format --check` (caught by qa, not at commit). Before each commit of teammate work, run `uv run ruff check . && uv run ruff format --check .` yourself — don't trust the "clean" report to cover formatting.

### Anchor runtime-state .gitignore patterns to the repo root
A bare `memory/` (for Johnny's runtime memory dir) silently matched `tests/memory/`, un-tracking the entire Phase 1 test suite. Root-anchor private runtime dirs as `/memory/`, `/data/`, `/snapshots/`, `/backups/` so they never collide with `tests/<name>/`.

### Point an @live token-budget guard at the PRIMARY provider, not a rambling local fallback
A cloud-first structured-output role (e.g. Groq primary ⇄ local-qwen fallback) should have its `@live` token-budget guard on the **primary (Groq) path** — the one production uses, which returns clean JSON. Local "thinking" models (qwen3.5) emit a **non-deterministic** reasoning ramble before structured output: a fixed `max_tokens` is intermittently blown (`finish_reason='length'`, no JSON → a *flaky* guard), and enough headroom for the worst-case ramble (~8k) blows the wall-clock timeout (4096 already took ~154s). Do NOT chase "reliable structured output from the local model" via a bigger token ceiling — that path is *by-design* "tired" degradation (SPEC §10: Groq down → simpler/local). Cover the fallback with a **deterministic graceful-degradation** assertion instead (stub the router to raise `LLMUnavailable` / return unparseable content → assert the role drops to its designed fallback — deterministic fact / keep-current / empty review — and the loop still completes), not an `@live` "local returns clean JSON" assertion. Phase 4 burned a long endgame discovering this: the token bump + per-model timeout are still correct improvements, but the *guard* belonged on Groq. Making a local thinking-model reliable for structured output needs `/no_think` (suppress its reasoning channel) — a provider-level mechanism, tracked separately.

### Per-model inference timeout: never let an offline heavy role's wall-clock leak onto the hot path
The local reasoning model (qwen) legitimately takes ~120-160s for a big structured completion; the per-tick fast model (gemma4) must fail over fast. A single global `LOCAL_LLM_TIMEOUT` forces a bad trade: raise it for the heavy offline roles and every hot-path failover slows; keep it tight and the offline roles time out. Fix is a **per-model timeout** — `local_reasoning_timeout` (~240s) applied only when the call targets the reasoning model, fast model keeps the tight budget (an `httpx` per-request `timeout=` hook on the provider). SPEC §10 already routes fast vs reasoning differently; the timeout should follow the same split.

### Reasoning-capable models need generous max_tokens for structured output — and a LIVE test to prove it
gemma4 (not just qwen) emits an internal reasoning chain before its answer when given a complex prompt + a JSON schema. With a tight `max_tokens` (e.g. 220) the reasoning consumes the entire budget → `content=""`, `finish_reason="length"` → no JSON → router schema-validation fails → (single-step provider chain) `LLMUnavailableError` → the feature silently produces nothing on every call. Set `max_tokens` with headroom for reasoning + the structured wrapper (the narrator needed ≈800–1024; reasoning ~250 + the JSON `{"thought": …}` fit comfortably), and make it a setting. CRUCIAL: deterministic/canned-router tests pass regardless of the token budget, so they CANNOT catch this — a `@pytest.mark.live` end-to-end test (real model, real budget) is required to cover the real-token path. Same family as the Phase-0 qwen empty-content artifact.

### Pin `asyncio_default_fixture_loop_scope` for DB-backed async suites (or the suite flakes)
With `pytest-asyncio` `asyncio_mode=auto` and the fixture loop scope UNSET, an async fixture can run on a different event loop than its test → a process-global async engine binds to the wrong loop → a *rotating* subset of DB tests fails under the full suite while each passes in isolation (non-deterministic = flaky CI; a lucky-green run masks it). Pin `asyncio_default_fixture_loop_scope = "function"` in `pyproject [tool.pytest.ini_options]` to keep each test's fixtures + body on one loop (safe when there are no session-scoped *async* fixtures). Validate with the full suite run **3×** (one green run isn't proof of determinism).

### Run DB/Redis-backed tests in-network (`./ctl.sh test`), not host pytest
Memory/DB tests reach Postgres/Redis at the compose hostnames `postgres`/`redis`, which only resolve inside the compose network. Host `uv run pytest` can't connect → ~25 connection ERRORS that look like failures but are purely environmental. The authoritative suite run is `./ctl.sh test` (in-network). Host pytest is fine for pure-unit/contract tests (no DB), and the lint/format gate runs anywhere. Same family as the Phase-0 live-health-leg (host-skipped, in-network-passes).

### Only ONE `./ctl.sh test` runner at a time — concurrent runs corrupt the shared test DB
`ctl.sh test` always targets the single `johnny5_test` database, and each DB-backed test `TRUNCATE`s + re-seeds its tables per function. Two runners at once (e.g. the lead running `pytest -q` while a teammate runs `./ctl.sh test`, or two teammates both running it) interleave their truncates and inserts → `IntegrityError` in a *rotating set* of memory/restart/semantic tests that **pass cleanly in isolation**. This masquerades as the documented loop-scope flake or a product regression, but it's neither — it's DB contention. Tell-apart signature: `IntegrityError` (constraint violation), not "attached to a different loop". Before trusting a red full-suite run, check `ps`/`docker ps` for a second `pytest`/`johnny5-api-run` process. In a team, coordinate an explicit single-runner DB window (lead sequences it). Real fix for the backlog: a `flock` guard in `ctl.sh test` (refuse/queue a second run) or per-run DB isolation so concurrent runs can't collide.

### Verify the live inference contract before writing clients (don't trust the spec doc)
The original SPEC assumed `qwen3.5:9b` + TEI-native embeddings + a `:8001` replica + Qwen vision. Reality (probed live): no such model tag, a custom `/embed` server, no replica, Qwen text-only / gemma4 multimodal, and Ollama had silently fallen back to CPU. Probe `inference.lan` + capture real response envelopes as fixtures before building adapters — contract tests fed by captured wire shapes catch doc drift (qwen returns `content`+`reasoning`, not empty content as first documented).
